## Health, status and scheduler endpoints — exact contracts

| Endpoint | Source/authentication | Actual signal and failure interpretation |
| --- | --- | --- |
| `GET /api/health` | `src/app/api/health/route.ts` accepts public requests. Its *expected* secret is `process.env.HEALTH_TOKEN ?? process.env.WORKER_TOKEN`; its *supplied* value is `x-health-token` header, falling back to `x-worker-token` **only if the first header is absent**. | Executes `SELECT 1`. Public HTTP 200 `{"ok":true}` or HTTP 500 `{"ok":false}`; no latency exposed. When the supplied secret matches a configured expected secret, response also includes numeric `latencyMs`. This authenticated mode calls `recordHealthSnapshot`, inserting/trimming `health_snapshots` (keeps newest 500). A snapshot-write failure is caught and does *not* change successful liveness into a 500. Public mode does not record history. |
| `GET /api/status` | `src/app/api/status/route.ts`. Public by default; detailed mode needs `OPERATIONAL_STATUS_DETAILS_ENABLED=true` **and** correct `x-readiness-token` for `operationalSecret("readiness")`. | Latest `health_snapshots` row produces public `{"ok":true}` or `{"ok":false}`. Missing snapshots also return `{"ok":false}`; DB query failure returns 503. Approved detailed response uses at most 200 most recent samples for an *observed* 24-hour percentage, median latency, current time/state and up to 48 history rows. It is not independent external uptime, and should not be exposed anonymously. |
| `GET /api/jobs/status` | `src/app/api/jobs/status/route.ts`. **Only** `x-scheduler-monitor-token` matching `SCHEDULER_MONITOR_TOKEN` (32+ bytes, distinct from effective worker secret); **no worker-token fallback**. | Missing/short/reused monitor config → HTTP 503; invalid header → 401; `CENTRAL_SCHEDULER_ENABLED` OFF → 503 `scheduler-disabled`. ON: reads `scheduler_state` records `delivery-drain` and `central-scheduler-lease`; recent completed run ≤10 minutes and recognized `running`/`completed` lease required. Failed/missing/stale lease → 503; independent `checkPayrollWorkerDispatchGate` may return 503 `payroll-worker-unhealthy`. Only fully healthy path returns 200 and `ok:true`. No job payloads or tenant data are returned. |
| `GET /status` | Public HTML/RSC in `src/app/status/page.tsx`. Server reads only newest `health_snapshots.ok`. | Shows **Operational**, **Degraded**, or **Unknown** badge; App + database scope, navigation and footer. It does not render latency, timestamps or historical diagnostics. Unknown is displayed on empty/failed snapshot read, even though public `/api/status` returns `ok:false` on empty history. Not an SLA or proof of email, PayMongo, bank payouts, BIR, SSS, PhilHealth or Pag-IBIG availability. |

**Important health token fallback:** `??` is **nullish**, not “empty string” fallback. If `HEALTH_TOKEN` is present but blank, the route does not substitute `WORKER_TOKEN`; if the health header is present but wrong, the worker header is not checked. If `HEALTH_TOKEN` is undefined, the route *can* accept a worker secret, but **never put `WORKER_TOKEN` in an external monitor** because it has privileged uses elsewhere. Use a separate strong `HEALTH_TOKEN` with header **`x-health-token`**, stored only in the uptime provider's secret store. A public HTTP 200 does not prove the monitor authenticated: require numeric `latencyMs` in addition to `ok:true`. Do not put any tokens in the URL, screenshots, retained headers or GitHub comments.

## External uptime monitor: `/api/health`

An authorized operator configures one independent HTTPS GET monitor against the exact independently verified deployed origin, path `/api/health`, approximately every 60 seconds. Monitor private header: `x-health-token` = dedicated `HEALTH_TOKEN`. Require TLS, no redirects, HTTP 200, JSON `ok === true`, and `latencyMs` that is a number. Page the designated on-call owner for HTTP 500, network/TLS failure, unexpected JSON or missing authenticated latency. Configure and actually test independent pager delivery; a green source endpoint by itself cannot notify anyone.

Authenticated probes *write* an availability snapshot through `src/lib/scheduler.ts::recordHealthSnapshot` (INSERT + pruning DELETE). This requires reviewed schema and DB privileges; **no ad-hoc production GRANT** to fix it. A swallowed snapshot error means `/api/health` can be green while `/status` is Unknown or stale. Independently verify fresh snapshot timestamps through approved private status diagnostics. An additional anonymous GET may check only HTTP up/down without storing history, but cannot satisfy authenticated-snapshot verification.

## Error tracking — Sentry reference vs. existing safe OTLP (default OFF)

**Current source has NO Sentry/error-tracking SDK or dependency in `package.json`.** Nothing in this PR installs one. `src/instrumentation.ts` uses Node-only `onRequestError()` and drops the unhandled error object, request, path, cookies, stack and headers. The only optional outbound route is `src/lib/safe-otel-error.ts`. The exact opt-in `SAFE_OTEL_ERRORS_ENABLED=true` is registered in `src/lib/critical-release-flags.ts`; `.env.local.example` explicitly sets **`SAFE_OTEL_ERRORS_ENABLED=false`**, with blank `OTLP_LOGS_ENDPOINT` and `OTLP_LOGS_BEARER_TOKEN`. The default path sends **zero error events to an external collector**.

### Existing privacy-safe OTLP alternative

With an independently approved operator/DPO change only, the existing sender may use:
- `SAFE_OTEL_ERRORS_ENABLED=true` — only literal lowercase `true` activates it.
- `OTLP_LOGS_ENDPOINT` — **HTTPS** public-DNS collector URL ending `/v1/logs`, without URL credentials, fragments or query parameters; `src/lib/security-network.ts` validates outbound destination/DNS. No localhost or unapproved alternate destination.
- `OTLP_LOGS_BEARER_TOKEN` — dedicated private 32+ character collector token, **not** `WORKER_TOKEN`, `HEALTH_TOKEN`, `READINESS_TOKEN` or an encryption secret. It is used solely in the outbound **Authorization: Bearer** header to the collector; the bearer must never enter log **body**.

The OTLP payload is a **fixed allowlist**: generated UUIDv4 request ID, fixed `web`/`scheduler` subsystem, fixed `UNHANDLED_SERVER_ERROR`/`CRON_TICK_FAILED` code, event `sanitized_server_error`, timestamp, fixed service name and severity. `safeOtelRecord` **preserves syntactically valid UUIDv4 request IDs**, regenerates invalid/non-v4 IDs, and discards unknown runtime properties even if TypeScript checks were bypassed. UUID format is **not an authentication or provenance check**: callers must create the request ID server-side rather than passing through user-supplied UUIDs. The current `src/instrumentation.ts` path creates its own ID using `newOperationalRequestId()`. No raw Error, message, stack, request URL/path/body, header, cookie, arbitrary context, tenant/employee identity, bank or government data is serialized. Failed/invalid collector config yields `misconfigured` or `failed` without failing the original app request; the exporter has a bounded delivery deadline. Approval also requires reviewing provider retention, processor agreement, allowed geography, secret access, network destination and synthetic-event proof. Disabling the flag stops **new** emissions but does not retroactively delete stored provider records.

### Sentry reference — future server-only implementation, not part of this PR

If Sentry is selected, a **separate** reviewed implementation must initialize **server-side only** on the approved Node path (no browser/Edge SDK, session replay, automatic performance URL/SQL tracing, request capture or PII breadcrumbs). **Mandatory pre-transport scrubbing** covers nested HTTP request/response bodies, URL/path/query params, all headers, auth and session cookies, exception text/stacks/causes, breadcrumbs, `user`, `contexts`, `extra`, `tags` and integration-added metadata. Prefer **constructing a new fixed-enum synthetic event from trusted fields** rather than handing raw Error/request objects to SDK hooks. If any unknown nested structure or SDK integration might bypass that allowlist, **drop the entire event before the network call**; disabling scrub failure is not a permissible fallback. No SDK/DSN/environment variable for Sentry exists or is added here. A future PR needs mocked transport tests for nested, alternate-case and encrypted values *and* a server-only/disabled-mode proof before production consideration.

## Job and queue health — not the same as uptime

`GET /api/jobs/status` is a **read-only**, monitor-token-only scheduler heartbeat and payroll worker dispatch preflight. It does **not** execute a tick and must not expose individual jobs. `src/lib/scheduler-liveness.ts` requires `delivery-drain` completed within **10 minutes**, lease status `running` or `completed`, with 503 on missing, failed, stale or invalid-clock evidence. The `CENTRAL_SCHEDULER_ENABLED` flag is independent of `WORKER_ENABLED`; source and `deploy/scheduler/README.md` keep them **OFF** until staging/release approval.

`src/lib/payroll-worker-dispatch-gate.ts` additionally checks `payroll-queue-worker-heartbeat` via `src/lib/payroll-worker-health.ts`. `PAYROLL_WORKER_HEARTBEAT_REQUIRED=true` makes that 10-minute heartbeat mandatory; on `VERCEL_ENV=production`, failure to require it blocks with `heartbeat-not-required`. On nonproduction with the policy OFF, `not-required` is not evidence that the real payroll worker runs. A green scheduler lease **cannot** prove payroll queue depth, age, failure backlog, idempotent payroll release, or that a real worker drained `payroll_jobs`. Queue-backlog metrics require a separate reviewed **aggregate-only** internal implementation; do not invent them in the public status UI.

### Independent watchdog

Use `node scripts/scheduler-watchdog.mjs` on a **different provider/host/failure domain** from the web app and worker as directed by [deploy/scheduler/README.md](scheduler/README.md). Its existing env vars are `SCHEDULER_WATCHDOG_STATUS_URL` (HTTPS, exact `/api/jobs/status`), `SCHEDULER_WATCHDOG_STATUS_HOST` (pinned host), `SCHEDULER_MONITOR_TOKEN` (read-only monitor secret), `SCHEDULER_WATCHDOG_ALERT_URL` (private HTTPS Slack-compatible webhook), `SCHEDULER_WATCHDOG_ALERT_HOST` (separately pinned alert host), `SCHEDULER_WATCHDOG_LABEL` and `SCHEDULER_WATCHDOG_POLL_MS` (default 60000; only 30000–120000). No DB URL or worker/cron token belongs on the watchdog.

The watchdog checks HTTP, bounded JSON, fixed state, **its own-clock** absolute last completed scheduler timestamp (≤10 min) and tolerance for clock skew—not just the HTTP 200 code. It GETs only, never invokes `POST /api/jobs/tick`. After **two failed polls**, a single **DOWN** webhook is sent; delivery is retried if failed. After **two successful polls** it sends **RECOVERED**. Its outbound alert contains only fixed safe reason enums, a bounded label and time, not target URLs, HTTP bodies or employee data. **Also monitor the watchdog itself from a third-party uptime/provider-process check**: host or webhook failures cannot alert themselves. See `tests/scheduler-watchdog.test.mjs` for synthetic source tests.
