## Step 3 — enrollment authorization and review (source-only)
- Canonical `POST /api/benefits` already authenticates the session, rejects cross-origin browser mutations, enforces `PEOPLE_PAYROLL_ROLES` plus custom role permissions and organization-session policy, resolves active employer membership, restricts employee records by employer, and checks the employee's organizational-unit scope. An unscoped employee or manager is not an authorized benefits operator. The existing HMO enrollment form writes through the same canonical POST.
- This isolated draft now ties *administrator review* to the selected legal employer, employee, plan, exact centavo amount and real ISO calendar date; a changed field, refreshed data or a new selection invalidates the review. Both generic benefits and HMO entry screens enforce the review **only while `BENEFITS_LOANS_UI_ENABLED` is ON**. Flag OFF maintains the prior enrollment behavior. The optional UI defaults effective dates to today's Asia/Manila calendar date; legacy flag-OFF defaults are preserved.
- These UI acknowledgments are **not employee consent** and are not authoritative server-side gates: direct requests to the existing signed enrollment API do not carry a verified employee election, consent evidence ID, immutable source record or independent approval. `benefit_enrollments` has no dedicated consent-evidence field. Do not claim verified consent or enable the optional UI based on this checkbox alone.
- Before activation, HR/Finance/DPO must decide which benefit categories require explicit employee election and lawful deduction consent; define a protected, auditable employer/employee/plan/amount/effective-date evidence reference and a backend verification gate that cannot be bypassed through `/api/benefits` or HMO enrollment. Retain immutable actor/date/authorization decisions subject to the approved legal/privacy policy. Independently test absent/expired/wrong-employer consent, employee revocation, inactive plans, invalid/backdated dates, and effective-date policy.
